02 / DEFECT RECORDS

Configuration and rendering

BUG-01 · Environment settings loaded after initialization

HIGH · P1FIXED / RETESTED

Precondition: Fresh Python process; database and JWT settings supplied through a synthetic dotenv file rather than inherited environment variables.

Reproduce: 1. Set a distinct SQLite URL, signing key and token lifetime in the fixture. 2. Import intake.main. 3. Compare initialized database/auth values with the fixture.

Expected: Application initialization uses the configured values.

Actual before fix: All three comparisons returned false. The default database and authentication settings were captured before dotenv loading.

Impact / cause: Local configuration can silently target the wrong database or use an unintended signing key. Dotenv was loaded from the response generator after dependent modules initialized.

Resolution: Shared early configuration loader imported before environment-dependent initialization. After-fix comparisons all returned true.

Trace: core/config.py, db/database.py, auth/web_session.py · tests/test_configuration.py · Evidence: before.txt / after.txt.

BUG-02 · Queue data rendered as raw HTML

HIGH · P1FIXED / RETESTED

Precondition: Controlled conversation response containing markup in a customer display field.

Reproduce: 1. Set user_id to <img src=x onerror=alert(1)>. 2. Invoke renderQueue in the dashboard harness. 3. Inspect the generated markup.

Expected: The supplied value is displayed as text, without creating an HTML element.

Actual before fix: The queue output contained a raw <img> element.

Impact / cause: An HTML injection sink in the agent interface creates potential script-execution risk when attacker-controlled data reaches it. API values were interpolated directly into innerHTML.

Resolution: Escape queue fields and message roles. Retest confirms raw markup is absent. The harness does not execute the payload or claim browser exploit verification.

Trace: dashboard/index.html · tests/dashboard.test.cjs · Evidence: dashboard-comparison.txt.

03 / DEFECT RECORDS

Agent state and handoff

BUG-03 · Conversation status badge does not update

MEDIUM · P2FIXED / RETESTED

Precondition: An agent opens a conversation whose API status is WAITING_FOR_AGENT; the global status property is a string.

Reproduce: 1. Initialize the dashboard harness with status: ''. 2. Return the conversation from the API stub. 3. Call openConversation. 4. Inspect the status element.

Expected: The visible badge reflects the API conversation status.

Actual before fix: The element was unchanged; status_element_updated returned false.

Impact / cause: Agents cannot reliably see conversation state. The implicit global reference resolves to window.status instead of the element.

Resolution: Use document.getElementById('status'). Retest returns true for the element update, independently of the global property.

Trace: dashboard/index.html · Evidence: dashboard-comparison.txt; verified in a simulated DOM.

BUG-04 · Standalone greeting triggers human handoff

MEDIUM · P2FIXED / RETESTED

Precondition: An active bot conversation receives a standalone greeting such as hi.

Reproduce: 1. Classify hi. 2. Apply confidence scoring to the resulting intent. 3. Inspect escalate_to_human.

Expected: A recognized greeting remains with the bot; an actual support request still escalates.

Actual before fix: Intent was general with confidence 0.5, below the 0.6 handoff threshold. Escalation was true.

Impact / cause: Routine greetings unnecessarily enter the support queue. The classifier lacked a standalone greeting category.

Resolution: Match normalized standalone greetings after business intents. The retest reports greeting and escalation false. Regression cases cover Arabic/English greetings, mixed greeting/support messages and return-to-bot behavior.

Trace: ai_brain/intent_classifier.py · tests/test_greeting_handoff.py · Evidence: before.txt / after.txt.

The greeting and status fixes were already present locally at the start of the original review; they were preserved, verified and included in PR #32.
